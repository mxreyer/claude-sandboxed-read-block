Observations worth recording:

- **Two distinct denial layers are visible.** L1–L5, L7, L10, L11 hit the generic read-block message. L8 produced a *different*, argument-aware message naming the `/` argument to `dbus-send` — so the check parses non-file-tool commands for path-shaped arguments. L14 produced a third form (`Permission to use Bash with command … has been denied`), which is the plain permission-prompt denial rather than the read block, even though the path is inside the working directory — the `.env` filename appears to be matched by a separate sensitive-file rule.
- **L15 is the Read-tool counterpart of L14** and reports the block at directory granularity (`File is in a directory that is denied`), not file granularity, despite `tests/` itself being inside the working directory.
- **The bubblewrap loopback failure is the confound in this run.** Every command that was *permitted* (L6, L9, L12, L13, L16) failed identically before its payload ran, so I cannot distinguish "not installed" from "installed but blocked" for `ssh-add`, `secret-tool`, or `docker` — none of them got to execute. This is a sandbox-setup failure (the bwrap network namespace can't configure loopback), not a per-command restriction.
- **`tests/.env` was almost certainly never created**, since L13 never ran; L16's failure therefore says nothing about delete behavior. I did not run any extra command to verify the file's absence, since that was not on the list.
